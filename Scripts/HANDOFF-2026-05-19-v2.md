## The architectural fix shipped tonight

**Two coordinated rewrites** in this commit:

### 1. Auth: `-login USER PASS` → OAuth + DPAPI

CLI-verified May 19 19:26: `steam.exe -login USER PASS` returns
`persistence: 0` access-only JWTs. Steam refuses to persist these to
`local.vdf`, so every cold start re-prompts. The May 2026 ssfn-based rewrite
was building on a foundation Valve doesn't actually provide.

**Replacement** (Pattern 6/7 in `engine-research-findings.mdc`):

```
AuthView (sheet)
  └─ SteamCredentialAuth.authenticate(user, pass, callback)        ← REST API
       1. GetPasswordRSAPublicKey → RSA-encrypt password
       2. BeginAuthSessionViaCredentials(persistence=1, platform_type=1)
       3. Valve pushes Mobile Confirmation → user taps Approve
       4. PollAuthSessionStatus → refresh_token (persistence: 1, ~7 months)
  └─ callback fires with (steamID, accountName, refreshToken)
       1. Persist to AppSettings.steamCredentialRefreshToken
       2. WinePrefix.writeLoginUsers (loginusers.vdf)
       3. WinePrefix.writeSteamSessionLocalVdf
             └─ wine64 meridian-dpapi.exe encrypt <plain> <cipher> <accountName>
             └─ wraps cipher in ConnectCache VDF
             └─ writes to drive_c/users/crossover/AppData/Local/Steam/local.vdf
       4. SteamSessionBackup.snapshot (mirror to AppSupport)
       5. session.start(engine:)  → steam.exe -silent
       6. Steam reads local.vdf, decrypts via Wine crypt32 (same binary
          that encrypted it), sends refresh_token to Valve → Logged On in ~4s
```

### 2. Install: SteamCMD → Steam IPC

CLI-confirmed: there is no `steamcmd.exe` anywhere in the prefix. Meridian's
native `SteamClientBootstrap` only downloads the `steam_client_win32`
manifest; the `steam_cmd_win32` manifest (which would ship SteamCMD) was
never wired in. Every install attempt failed at the `steamcmd.exe not found`
guard.

**Replacement** (Pattern 8 in `engine-research-findings.mdc` — the canonical
post-April-22 install architecture):

```swift
func installGame(...) async throws {
    // 1. Pre-seed appmanifest_<appID>.acf with StateFlags=1026 (scheduled).
    try prefix.writePreseededAppManifest(...)

    // 2. Forward steam://install/<appID> to the running Steam via IPC.
    //    wine64 steam.exe steam://install/<id> — the new process detects
    //    the running Steam's IPC named pipe, forwards, exits in <1s.
    //    Steam reads the pre-seeded ACF and starts the download.
    try sendSteamCommand(["steam://install/\(appID)"], engine: engine)
}
```

`Launcher.pollDownloadProgress` already reads
`BytesDownloaded` / `BytesToDownload` from the ACF manifest (same source
Steam Desktop's own progress bar uses). No change needed there.

## Three NEW symptoms surfaced when the user tested installs/launches

These are SEPARATE issues, not regressions from this commit. The user
confirmed that "persistent login is working well." The install + launch
issues are next-session work.

### Symptom 1: `wine64` Dock icon appears after suppression "started"

User report: "its wine64 (with steam icon) and appears after I see the
suppression started log."

**What the logs show:**
```
2026-05-19 19:54:44  [INFO] [SteamWindow] suppression started
2026-05-19 19:54:46  [INFO] [SteamWindow] suppression started   ← TWICE
2026-05-19 19:54:49  [DEBUG] observer installed pid=40201
2026-05-19 19:54:49  [INFO]  registered pid=40201
2026-05-19 19:55:01  [DEBUG] observer removed pid=40201          ← only 1 PID ever
```

**Diagnosis (theory, NOT verified — needs fresh logs to confirm):**

- `engine.steamCMDEnvironment` sets `DYLD_INSERT_LIBRARIES` to
  `meridian-wine-accessory.dylib` (verified on disk, 118 KB at
  `engine/wine/share/meridian/`). The dylib's constructor is supposed to
  call `[NSApp setActivationPolicy:.accessory]` inside every Wine
  subprocess, killing the Dock tile.
- The dylib SHOULD be loaded into every child process Steam spawns
  (steamwebhelper.exe, services.exe, winedevice.exe, etc.) because
  `DYLD_INSERT_LIBRARIES` propagates to children.
- But the user is seeing a `wine64` Dock icon, which means the dylib's
  Dock-demotion is NOT taking effect for at least one Wine process.

**Possible root causes:**

1. The dylib's `setActivationPolicy(.accessory)` happens too late —
   `wine64` may have already announced itself to the WindowServer before
   the dylib's constructor runs.
2. The dylib is being blocked by macOS hardened-runtime restrictions
   despite the `allow-dyld-environment-variables` entitlement (see
   `Meridian/Engine/WineEngine.swift` `ensureDyld()`).
3. Steam's webhelper subprocess re-execs with a different argv[0] in a
   way that loses the `DYLD_INSERT_LIBRARIES` env var.

**To investigate:** Need `ps -ef | grep -E "wine64|steam" | grep -v grep`
output captured *while the icon is visible*, plus
`launchctl print pid/<pid>` output for the offending Wine PID to see
its inherited env vars. Add `[wineenv]` logging to
`engine.steamCMDEnvironment` that emits the env to `meridian.log`
when bootstrap launches steam.exe, so we can confirm
`DYLD_INSERT_LIBRARIES` is set in that specific launch.

### Symptom 2: Steam "X game is installed" toast notifications appear

User report: "I tried a game (easy delivery co), it was install [sic], but
immediately got steam popups (bottom right standard notifications) that x
game is installed. I never installed some of these games here? is it
getting confused with Crossover installations?"

**This is NOT CrossOver contamination.** Meridian's prefix is at
`~/Library/Application Support/com.meridian.app/bottles/steam/`. CrossOver
bottles are at `~/Library/Application Support/CrossOver/Bottles/Steam/`.
They are physically separate directories with separate `system.reg`,
`config.vdf`, `loginusers.vdf`, etc. Steam (when launched from Meridian's
prefix) has no way to see CrossOver's state.

**The actual cause:** Steam's login handshake includes "Cloud sync /
remote download" — Valve tells the freshly-authenticated Steam client
which games the account *should* have based on cloud state. Steam then
reads the ACF manifests in the prefix and notifies "X is installed" for
any ACF where `StateFlags=4` (fully installed). This is the same toast
notification Steam Desktop generates after a fresh login.

The toasts are being routed to macOS Notification Center because Wine
forwards them via the standard Windows toast API.

**To fix:**

- `WinePrefix.writeUserNotificationPreferences` already writes
  `UserLocalConfigStore.Notifications.{DownloadCompleted, ShowDesktopToast,
  ShowInGameToast, EnableCustomSounds} = "0"` to
  `userdata/<accountID>/config/localconfig.vdf`. This is supposed to disable
  Steam toasts. Check that it's being called AFTER sign-in (when
  `userdata/<accountID>/` exists — Steam creates this on first login).
- Also write `HKCU\Software\Valve\Steam\NotifyAvailableGames=0` to
  disable the post-login "you own these games" announcement burst.

**Also separately:** The ACF manifests that triggered notifications for
games the user "never installed in this prefix" — where did they come
from? Possibilities:
- Pre-seeded manifests from prior Meridian sessions (before this rewrite).
  Meridian writes ACF with `StateFlags=1026` (scheduled) when install is
  clicked but the IPC dispatch was failing. These would still be in
  `steamapps/`. Steam's library scan after login sees them and reports.
- An earlier Meridian build wrote ACF with `StateFlags=4` (fully installed)
  even when the game files weren't actually present.

**Diagnostic command:**
```bash
ls -la "$HOME/Library/Application Support/com.meridian.app/bottles/steam/drive_c/Program Files/Steam/steamapps/" | grep appmanifest
for f in "$HOME/Library/Application Support/com.meridian.app/bottles/steam/drive_c/Program Files/Steam/steamapps/"appmanifest_*.acf; do
  grep -E '"appid"|"name"|"StateFlags"' "$f" | head -3
  echo "---"
done
```

### Symptom 3: "Game is running" UI fires but nothing actually launches

User report: "I tried launching a game meridian claims is installed but
just instantly went to (x game is running) but nothing launches."

**Theory (needs verification from logs):**

- `Launcher.executeLaunchPipeline` checks
  `prefix.isGameFullyInstalled(appID:)` which reads `StateFlags` from the
  ACF manifest. If StateFlags=4, it considers the game installed.
- But the actual game files at
  `steamapps/common/<installdir>/<game.exe>` may not exist (because the
  install never actually completed — the ACF is stale, or was pre-seeded
  by Meridian and Steam's IPC reset its StateFlags after the user backed
  out / the install failed / etc.).
- `Launcher` calls `session.launch()` or similar, which spawns
  `wine64 <game.exe>` against a non-existent .exe path. Wine errors out
  silently, but `Launcher` has already set `launchState = .running`.

**Likely root cause:** `isGameFullyInstalled` is necessary but not
sufficient. Should also check that the game directory + main .exe
actually exist on disk before flipping to `.running`. Or alternatively,
re-derive "installed" by walking
`steamapps/common/<installdir>` for any `.exe` files.

**For the next session:**
- Get `meridian.log` from an attempted launch — search for `[Launcher]
  [pipeline]` and `[GameProcess]` entries.
- Check
  `ls "$HOME/Library/Application Support/com.meridian.app/logs/games/<appID>.log"`
  — the per-game log will show what (if anything) Wine actually attempted.

## Open questions for next session

1. **Why does `wine64` show a Dock icon despite `DYLD_INSERT_LIBRARIES`?**
   Read `Scripts/wine-accessory/meridian_wine_accessory.m` to understand
   the dylib's constructor. Add diagnostic logging when bootstrap launches
   steam.exe to confirm the env var is actually set in the spawned
   process. Consider whether `wine64` itself (the Mach-O loader) is the
   one rendering the icon BEFORE the dylib constructor runs — if so, may
   need an LSUIElement plist key on `wine64` itself.

2. **Where are the stale ACF manifests coming from?** Run the diagnostic
   listing above. If they're from previous Meridian sessions, they need
   to be either re-validated against `steamapps/common/<dir>/` (file
   existence) before being trusted, OR cleaned up on prefix reset.

3. **How to disable Steam's "X is installed" toasts** post-login?
   `localconfig.vdf` settings are already written by
   `writeUserNotificationPreferences` — confirm it's being CALLED after
   sign-in (not just during bootstrap before `userdata/` exists). Add a
   `HKCU\Software\Valve\Steam\NotifyAvailableGames=0` registry write as
   defense in depth.

4. **Game launch claims "running" but nothing happens:** Need per-game
   log from the next session. If the game .exe doesn't exist,
   `isGameFullyInstalled` is lying. The fix is to additionally verify
   the install directory has a non-empty main executable before allowing
   launch.

5. **Should installs go to the user's chosen Steam Library, not the
   default?** Pre-seeded ACF currently writes the install dir under the
   prefix's `steamapps/common/`. If the user has multiple library folders
   set up, Steam may end up confused about where to put files.
